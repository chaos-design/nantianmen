# 首屏 LCP 调优记录

[中文](performance-lcp.md) | 开发手册见 [development-guide.md](development-guide.md)

本文记录 `/workspace`、`/editor/<id>`、`/r/<slug>` 三个首屏页面的 LCP 测量口径、
逐轮改动、前后数据，以及**没有通过验证因而撤回**的尝试。每一轮都只在上一轮已入库
的结果之上继续，所有数字都可以用第 6 节的方式复现。

## 1. 测量口径

仓库自带 `scripts/measure-lcp.mjs`（单端口多轮采样）。它的问题在于「先测基线、
再测优化」时，两次测量之间的机器状态会漂移：同一份代码隔十分钟复测，实测能差
150–250 ms（约 10–15%），小改动会被完全淹没。

因此配了 `scripts/measure-lcp-ab.mjs`：两个端口分别跑改动前 / 改动后的构建，
**每轮 A、B 相邻各测一次**，最后比中位数和配对差。本文的对比数据都来自它。

| 项 | 取值 |
| --- | --- |
| 构建 | `pnpm build` + `next start` 的生产产物 |
| 环境 | `RESUME_DATA_BACKEND=file` + 测试身份（`AUTH_TEST_*`），`NODE_ENV=test` |
| 数据 | `scripts/seed-perf-fixtures.mjs` 生成的固定简历：3 页 A4 + 一张 600×800 人像 |
| 视口 | 1280×720，DPR 1 |
| 网络 | `slow4g`（400 ms / 409 kbps），对比时另有 `fast3g`（150 ms / 1638 kbps） |
| CPU | 4× 降速 |
| 缓存 | 每次采样全新上下文 + `Network.setCacheDisabled` |

**口径的两个已知偏差**，读数字时必须一起看：

- `next start` 只跑 HTTP/1.1（生产走 HTTP/2）。HTTP/1 下每域名 6 条连接，样式表要和
  十几个 JS chunk 分同一条 409 kbps 管道，争用被放大；HTTP/2 有优先级树，样式表和
  首屏图不会被脚本排队拖住。所以本文的数字偏悲观，改动之间的**相对差**仍然可信。
- 慢网把「绘制开销」压到网络等待下面。反过来，在 `fast3g` 或不节流的机器上，CPU
  排在关键路径上的部分占比更高（见 2.3）。

## 2. 本轮改动

### 2.1 公开分享页的放置图改走图片优化器（第一轮，已入库）

`/r/<slug>` 在 slow4g 下的 LCP 元素是 A4 上的放置图，不是文字：源图是用户上传的
原图（测试夹具 600×800 JPEG，51 kB），A4 上只按 500×640 显示；首屏还要下载 24 kB
样式与 70 kB（gzip）JS，同一条 409 kbps 的管道上图片排在最后，5.1 s 才下完。

改动：公开快照的放置图统一走 Next 图片优化器（`/_next/image?url=…&w=…&q=75`），
按放置宽度取固定档位，`<head>` 的 `preload` 用同一个地址，保证预载就是实际请求。
同一个夹具：51 kB JPEG → 21 kB WebP。

只给单一地址、不铺 `srcSet`：先试过 `srcSet`（640w / 1080w）+ `sizes`，本地 e2e
出现「图片元素存在但始终没有 `naturalWidth`」——浏览器挑候选的分支一旦和预载地址
对不上就不请求，收益抵不过这个风险，退回单地址。

### 2.2 编辑器的私有资源按显示宽度转码（本轮）

`/editor/<id>` 的 LCP 元素和分享页一样是 A4 上的放置图，但它走不了公开优化器：
优化器以服务端身份去取源图，拿不到用户会话，私有资源会 401。

改动落在资源路由自己身上：`GET /api/resumes/<id>/assets/<id>?w=<档位>`

- **鉴权不变**：仍然先 `getPrivateAsset(resumeId, assetId, actor)`，转码只是「拿到
  字节之后」的一步，不存在为了转码放宽权限的路径。
- **只用白名单档位**（320 / 480 / 640 / 960 / 1280）。任意宽度都接受等于把一个
  公开的缩放放大器放进服务端；非法值直接回落到原图。
- **不放大**：`resize({ width, withoutEnlargement: true })`。夹具原图只有 600 宽，
  请求 1280 档位时输出仍是 600×800，只是重编码成 WebP。
- **先按 EXIF 摆正**（`rotate()`）：浏览器对原图会自动应用 EXIF 方向，转码之后这层
  兜底就没了，必须在服务端补，否则竖拍照片会躺倒。
- **只转位图**（jpeg / png / webp / avif / heic）。GIF 会在转码里丢掉后续帧，SVG
  本来就是矢量，两者都直接下发原图。
- **sharp 是 optionalDependency**：部署环境装不上原生二进制时 `import` 会失败，
  这里捕获后返回 `null`，路由回落到原图，不会 500。
- **进程内 FIFO 缓存**（96 条，键 = `资源 id @ 档位`）。资源 id 是一次上传生成一次的
  uuid、永不复用，所以不存在「同一 id 换了内容」的失效问题；丢缓存最多多转一次。

客户端跟着改：`src/shared/resume-image.ts` 里的档位表被图片层、预载和路由三处共用
（三处各写一套必然出现「预载地址 ≠ 实际请求」而多下一份）。图片层用**已提交的**
`placement.width` 取档，不用拖拽中的瞬时宽度——后者会在一次缩放手势里变出好几个 URL，
每帧触发重新下载。

实测同一夹具：51,133 B JPEG → 26,628 B WebP（−48%）；按 480 档位是 10,508 B。

### 2.3 工作台标题栏的背景模糊只在滚动后启用（本轮）

`/workspace` 的 LCP 是标题文字，`backdrop-filter: blur(18px)` 挂在 sticky 标题栏上，
未滚动时它背后只是本页顶部的平滑渐变——模糊一个渐变和原图几乎一样，却要多一次全宽
backdrop 采样和一个合成图层。

改动：把 `backdrop-filter` 移到 `.workspace-header[data-scrolled="true"]`。滚动后背后
才是真正的内容，模糊在那一刻才有意义，而那时标题栏早已离开首屏。

验证方式与结论要分开说：

- 视觉：与改动前逐像素比对，`/workspace` 桌面与移动端差异通道 **0.000%**（最大通道差
  2，压缩噪声级），`/r` 完全一致。
- 绘制开销：在同一套节流参数下把 CSS 从内存直接回放（不经过网络），LCP 中位
  **1384 ms → 1072 ms（−312 ms，−23%）**——这 312 ms 就是模糊的绘制成本。
- 但在 slow4g 的真实网络 A/B 里，这点绘制成本被网络等待盖住，**没有测出显著变化**
  （见第 4 节）。所以它没有被算进本轮的提升数据，只在 `fast3g` / 真实 HTTP/2 这类
  「网络不再是绝对瓶颈」的场景里兑现。

### 2.4 工作台首屏的三份数据改成同批发出（本轮）

`/workspace` 的页面里，简历列表和可见公告本来就在 `Promise.all` 里，但管理员额外需要的
「全量公告」是 `await` 在它们**之后**的第四步。也就是说管理员的首屏永远比普通用户多
一次串行往返，而这条路径在本地 file 后端下完全看不出来（读文件没有往返），只有接真实
Supabase 时才表现为 TTFB 变长。

改动：抽成 `loadWorkspaceData(actor, sources)`，三条读取同批发出，非管理员那条直接
`Promise.resolve(null)`。抽函数的目的不是分层，而是让「并发」变成可测事实——单测用
可控的 gate 卡住三条读取，断言「一条都没放行之前三条都已经开始」，串行实现会立刻失败。

这条不影响本地的 LCP 数字（没有网络往返可省），只在生产 TTFB 上兑现，所以没有算进
第 4 节的对比表。

## 3. 撤回 / 未通过的尝试

- **`experimental.inlineCss`**：想用它把渲染阻塞的样式表请求彻底去掉。实测 Next 15.5
  的实现在这里把**全站 CSS** 都内联进每个页面：`/workspace` 的 HTML 从 39 kB 涨到
  252 kB，`/editor` 从 128 kB 涨到 451 kB。409 kbps 下光是 HTML 就要 5–9 s，方向
  直接相反，已撤回，`next.config.ts` 保持原样。
- **工作台「新建简历」弹窗按需加载**（上一轮）：拆成独立模块 + `next/dynamic`
  （`ssr: false`），预期把 Radix Dialog 从首屏 chunk 里摘出去。实测 `/workspace`
  首屏 JS 只从 184.0 kB 降到 183.8 kB——Radix 原语同时被工作台其它组件用着，webpack
  仍把它留在共享 chunk 里。净收益 0.2 kB，不值得多三个文件，已撤回。
- **非首屏 A4 分页 `content-visibility: auto`**（上一轮）：A/B 无收益且增加排版抖动。

## 5. `/workspace` 的下限在哪里

这个页面的 LCP 元素是标题文字，形状和另外两个不同：它不加载任何图片，等的是
「HTML + 样式表 + 主线程空闲」。为了把「还剩下多少可省」问清楚，加了
`scripts/measure-lcp-breakdown.mjs`：按资源类别把请求 abort 掉再测，看 LCP 变化。

同样 slow4g / 4× CPU / 3 轮中位（`.data/perf/results/lcp-breakdown-*.json`）：

| 场景 | LCP 中位 | 说明 |
| --- | --- | --- |
| `baseline` | 2680 ms（2476–2928） | HTML 8.9 kB + CSS 20.0 kB + JS 195 kB（含 gzip 前字节） |
| `no-script` | 1988 ms（1980–2036） | 阻断全部框架 JS：**JS 占约 690 ms** |
| `no-css` | 864 ms（828–872） | 阻断两份样式表：**样式表占约 1.8 s** |

这张表把权重说清楚了：**渲染阻塞的样式表才是这个页面的主要成本（1.8 s），不是 JS
（0.69 s）**。样式表的 1.8 s 由三部分组成：一次往返（400 ms）、20 kB 在 409 kbps 上
的传输（约 390 ms）、以及 4 倍降速下的样式解析与首帧排版。JS 的 0.69 s 则来自它和
样式表抢同一条管道，所以「拆 JS」能省下的上限就是这 0.69 s，而实测阻断 85 kB 的
交互型 chunk 已经在噪声内（见下）。

三条结论：

1. **框架 JS 是基线**：184 kB(gzip) 里 98.8 kB 是 React / ReactDOM / Next 客户端运行时
   本身，剩下的是 Radix 原语（35 kB）、sonner（10 kB）和页面代码。没有「不水合也能
   首屏」的选项。
2. **逐块拆 JS 不划算**：把 85 kB 的交互型 chunk 全阻断，LCP 在噪声内（2856 ms vs
   2732 ms）。这些 chunk 不是排队卡住样式表的元凶。
3. **样式表这一块也压不动**：要再往下走只有两条路——把 CSS 内联进 HTML（`inlineCss`
   在本仓库会把全站 CSS 都塞进每个页面，方向相反），或者让样式表不阻塞首屏（需要
   绕开 Next 的样式管线手动接管 `<link>`，代价是失去构建期的 CSS 去重与顺序保证，
   不值得）。Tailwind 的工具类被全站共享，按路由再拆只能省几 kB。

所以这个页面停在「架构基线 + 内容本身」，没有继续硬凑。`/r` 与 `/editor` 的收益
来自真正可省的字节（图片从 51 kB 降到 21 / 26.6 kB），两者性质不同。

> **第四轮修正**：上面第 3 条只说对了一半。样式表的**写法**确实压不动，但「哪些样式
> 算进这一页」是可以压的——第四轮把编辑器与 A4 渲染器专用的规则从 `core.css` 搬走，
> `/workspace` 的首屏 CSS 少了 11.5 kB（原始）。更关键的是，第一次把「CSS 到底值多少
> 毫秒」量成了可复现的实验，而不是估算。见第 7 节。

## 6. 复查方式

```bash
pnpm build
# 改动前：把当前 HEAD 复制一份到 /tmp/nm-b 并构建，或用 git stash 前的构建产物
# 两个端口都指向同一份 file 后端与同一批夹具
node scripts/seed-perf-fixtures.mjs http://127.0.0.1:3210

node scripts/measure-lcp-ab.mjs \
  --a http://127.0.0.1:3211 --b http://127.0.0.1:3210 \
  --runs 9 --net slow4g
```

结果落在 `.data/perf/results/lcp-ab-*.json`。单端口多轮采样用
`scripts/measure-lcp.mjs`。

想知道「这个页面还剩下多少可省」，用分解脚本按资源类别看：

```bash
node scripts/measure-lcp-breakdown.mjs --route /workspace --runs 3 --net slow4g
# 也可以按 chunk 名逐个试：--block 7092,5989,473
```

它只注册需要拦截的 URL 模式。**不要**把它改成 `page.route("**/*")` 全量代理——全量
代理会让每个请求都绕一次 Playwright 调度，实测把 baseline 自己抬高 600 ms 以上，
比要测的差异还大（这个坑踩过一次，脚本注释里留了记录）。

私有资源的转码可以单独验：

```bash
curl -s -o /dev/null -w "%{size_download} %{content_type}\n" \
  "http://127.0.0.1:3210/api/resumes/<resume-id>/assets/<asset-id>"          # 51133 image/jpeg
curl -s -o /dev/null -w "%{size_download} %{content_type}\n" \
  "http://127.0.0.1:3210/api/resumes/<resume-id>/assets/<asset-id>?w=640"    # 26628 image/webp
curl -s -o /dev/null -w "%{size_download} %{content_type}\n" \
  "http://127.0.0.1:3210/api/resumes/<resume-id>/assets/<asset-id>?w=700"    # 51133 image/jpeg（非法档位回落）
```

## 7. 第四轮：LCP 的关键路径是样式表，不是 JS

这一轮先做「归因实验」再动手，避免又出现「改了一堆、指标不动」。

### 7.1 两个互相印证的实验

**实验 A：把 utilities 层从 CSS 里拿掉，看 LCP 掉多少。**
`scripts/measure-css-ab.mjs` 用路由拦截把 `core.css` 换成删掉 `@layer utilities` 的版本
（当时的构建是 83.0 kB → 37.5 kB 原始 CSS；第 7.2 节搬完样式后同一份产物是
73.6 kB → 28.0 kB），其余请求不变，A/B 相邻采样：

| 轮次 | 完整 CSS | 去掉 utilities |
| --- | --- | --- |
| 6 轮配对 | 2588 ms（2580–2632） | **1692 ms（1648–1772）** |

配对中位差 **−920 ms**，区间不重叠。折算约 **108 ms / kB(gzip) CSS**。

**实验 B：先砍 15.1 kB 首屏 JS，再测。**
把发布状态筛选从 Radix Select 换成原生 `select`、sonner 改为按需加载，首屏 JS
185.1 → 170.0 kB(gzip)。交错 A/B 9 轮配对差 **0 ms**（2588 → 2588）。

两个实验放在一起说明：**这一页的 LCP 由渲染阻塞样式表的字节数决定，JS chunk 在
CSS 之后才下载，动它不影响首屏**。上一轮「逐块拆 JS 在噪声内」的观察是对的，但结论
下错了——不是「没有可省的」，而是「可省的在 CSS 里」。

### 7.2 改动

1. **发布状态筛选改为原生 `<select>`**（三个固定选项）。原来这一控件把整套 Radix
   Select 拉进首屏（22.9 kB chunk）。外观在 `workspace.css` 里对齐（高度、边框、
   背景、chevron 位置一致），1280×900 逐像素比对差异 0.057%（就是控件本身）。
2. **sonner 移出首屏**：`src/lib/notify.ts` 在第一次提示时动态 `import("sonner")`，
   `LazyToaster`（`next/dynamic` + `ssr: false`）在 hydration 之后挂载。工作台 5 处
   `toast.*` 改为 `notifySuccess/notifyError`，语义不变。
3. **`core.css` 按「谁真的渲染」拆分**：
   - `.resource-*` / `.style-*` → `editor.css`（只有编辑器渲染）
   - `.template-*` / `.public-a4-*` / `@media print` → `resume.css`（只有 A4 渲染路由用）
   - `.template-thumbnail-*` 留在 `core.css`：工作台的新建弹窗也渲染缩略图
   工作台首屏 CSS 18.8 → 17.0 kB(gzip)，原始 CSS 少 11.5 kB。
4. **`/r` 去掉 Toaster 与 toast**：复制结果直接在按钮上回显「已复制」，省掉 sonner。

首屏字节（同一构建口径，gzip）：

| 页面 | JS | CSS | 合计 |
| --- | --- | --- | --- |
| `/workspace` | 185.1 → **170.0** kB | 18.8 → **17.0** kB | 204.0 → **187.1** kB（−16.9） |
| `/r/<slug>` | 129.0 → 128.5 kB | 23.2 → 22.1 kB | 152.3 → 150.6 kB（−1.7） |
| `/editor/<id>` | 267.8 → 269.8 kB | 29.3 → 28.8 kB | 297.1 → 298.6 kB（+1.5，chunk 重新划分） |

### 7.3 数据（交错 A/B，9 轮，slow4g / 4× CPU）

| 页面 | 改动前 | 改动后 | 配对中位差 |
| --- | --- | --- | --- |
| `/workspace` | 2608 ms（2592–2648） | **2448 ms（2336–2592）** | **−152 ms（−6.1%）** |
| `/r/<slug>` | 3104 ms（3012–3296） | 3024 ms（2860–3316） | −84 ms（−2.6%） |
| `/editor/<id>` | 3748 ms（3408–5468） | 3756 ms（3432–4320） | −4 ms（噪声） |

`/workspace` 单独复测过一轮 9 轮配对：2632 → 2456 ms，配对 −176 ms，前后区间不重叠。
两轮的方向和量级一致（−152 / −176 ms），与「CSS 少 1.8 kB(gzip) ≈ 190 ms」的折算吻合。

### 7.4 结论与仍然存在的边界

- **`/workspace` 首次进入 2.5 s 以内**（2448 ms 中位）。它的 LCP 元素是标题文字，
  关键路径是「HTML → 渲染阻塞 CSS → 首帧排版」，这轮把 CSS 里不属于这一页的部分
  搬走，收益兑现了。
- **`/r` 与 `/editor` 的 LCP 是 A4 上的图片**，首屏总量 150.6 / 298.6 kB。在
  409 kbps 的管道上，仅把全部字节传完就需要 2.9 / 5.7 s；2.5 s 以内的前提是
  「图片与 CSS 只和很少的脚本抢带宽」。这两页这轮没有针对性的字节改动
  （图片质量、档位、是否上 AVIF 都是产品决策），所以持平 / 小幅波动。
- 同一份代码在 `fast3g` 下三页分别是 1.42 / 2.22 / 1.65 s，均达标。slow4g 是本仓库
  刻意偏悲观的口径（HTTP/1.1 + 409 kbps），改动之间的相对差仍然可信。

### 7.5 试过但没做的：按路由裁剪 Tailwind utilities

这一轮之后，`core.css` 里还剩约 8.5 kB(gzip) 的 Tailwind 工具类，而 `/workspace`
实际只用到其中三分之一左右。按 108 ms/kB 的折算，这里看起来还有几百毫秒。

先做了替换实验再决定要不要动构建：用 import 图给 `/r` 编了一份 scoped core
（13.1 → 6.8 kB gzip，原始 CSS 46.8 → 36.1 kB），在同一个 slow4g 管道的浏览器里
把它替换进 `core.css` 的位置，6 轮配对：

| 轮次 | 完整 core | scoped core |
| --- | --- | --- |
| 6 轮配对中位 | 4080 ms | 3552 ms |

配对中位差 −156 ms，但样本区间是 −2284 ~ +1608 ms。**这个量级不是噪声问题，是机制
不同**：`/r` 的 LCP 元素是图片，CSS 只是和图片抢同一条 409 kbps 的管道。少 6.3 kB
相当于把排队字节从 150 kB 降到 144 kB（约 4%），只能按比例缩短图片的等待时间；
`/workspace` 的 LCP 是文字，CSS 直接决定首帧时间，少 1 kB 就是实打实的 100 ms。
所以给 `/r` 裁 CSS 换不来 2.5 s，要让这一页达标只能动图片本身的字节
（质量、档位、AVIF），那是产品决策，不在这一轮的范围里。

`/workspace` 的 scoped 版本能到约 10.2 kB（−2.9 kB），但只能靠**精确的 import 文件
列表**（按目录裁只能省 0.2 kB，因为 `components/ui` 是全量依赖）。这需要在
`next build` 前从 import 图生成 `@source` 清单，维护成本高于它带来的约 300 ms，
这轮没有做。如果以后要上，`scripts/measure-css-ab.mjs` 的替换实验可以先验证收益，
不必先改构建。
