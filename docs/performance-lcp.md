# 首屏 LCP 调优记录

[中文](performance-lcp.md) | 开发手册见 [development-guide.md](development-guide.md)

本文记录 `/workspace`、`/editor/<id>`、`/r/<slug>` 三个首屏页面的 LCP 测量口径、
本轮改动、前后数据和没有通过验证因而撤回的尝试。

## 1. 测量口径

仓库自带 `scripts/measure-lcp.mjs`（单端口多轮采样）。它的问题在于「先测基线、
再测优化」时，两次测量之间的机器状态会漂移：同一份代码隔十分钟复测，实测能差
150–250 ms（约 10–15%），小改动会被完全淹没。

因此新增 `scripts/measure-lcp-ab.mjs`：两个端口分别跑改动前 / 改动后的构建，
**每轮 A、B 相邻各测一次**，最后比中位数和配对差。本文的对比数据都来自它。

| 项 | 取值 |
| --- | --- |
| 构建 | `pnpm build` + `next start` 的生产产物 |
| 环境 | `RESUME_DATA_BACKEND=file` + 测试身份（`AUTH_TEST_*`），`NODE_ENV=test` |
| 数据 | `scripts/seed-perf-fixtures.mjs` 生成的固定简历：3 页 A4 + 一张 600×800 人像 |
| 视口 | 1280×720，DPR 1 |
| 网络 | `slow4g`（400 ms / 409 kbps）与 `fast3g`（150 ms / 1638 kbps） |
| CPU | 4× 降速 |
| 缓存 | 每次采样全新上下文 + `Network.setCacheDisabled` |

为什么必须节流：不节流时三个页面都在 200 ms 以内，改动差异全被噪声吃掉。
为什么基线要用 slow4g 看：本机 `fast3g` 下页面已在 1–1.5 s，剩余空间容易被
抖动掩盖；`slow4g` 更接近中低端机的真实形态，也是本轮唯一出现明显瓶颈的档位。

## 2. 本轮改动

### 2.1 公开分享页的放置图改走图片优化器

`/r/<slug>` 在 slow4g 下的 LCP 元素是 A4 上的放置图，不是文字：

- 源图是用户上传的原图（测试夹具 600×800 JPEG，51 kB），A4 上只按 500×640 显示；
- 首屏还要下载 24 kB 样式与 70 kB（gzip）JS，同一条 409 kbps 的管道上，
  图片排在最后，5.1 s 才下完，LCP 直接被它拖住。

改动：公开快照的放置图统一改走 Next 图片优化器
（`/_next/image?url=…&w=…&q=75`），按放置宽度取一个固定档位，`<head>` 里的
`preload` 用同一个地址，保证预载就是实际请求、不会多下一份。
同一个夹具：51 kB JPEG → 21 kB WebP（`q=75`，宽度不放大）。

只给单一地址、不铺 `srcSet`：先试过 `srcSet`（640w / 1080w）+ `sizes`，
本地 e2e 里出现了「图片元素存在但始终没有 naturalWidth」的情况——浏览器挑候选
的分支一旦和预载地址对不上就不会请求，收益也不足以抵消这个风险，于是退回单地址。

只对公开快照启用：私有资源要按 JWT 校验归属，而优化器是以服务端身份去取源的，
拿不到用户会话，走这条路会 401。

### 2.2 撤回的尝试

- **工作台「新建简历」弹窗按需加载**：把弹窗拆成独立模块、用 `next/dynamic`
  （`ssr: false`）加载，预期把它和 Radix Dialog 原语从首屏 chunk 里摘出去。
  实测 `/workspace` 首屏 JS 只从 184.0 kB 降到 183.8 kB——因为 Radix 原语同时被
  编辑器页使用，webpack 仍把它留在共享 chunk 里。净收益约 0.2 kB，不值得多三个文件
  和一次占位替换，已撤回。

## 3. 数据对比

交错 A/B，`/r/<slug>`，5 轮配对，slow4g（`.data/perf/results/` 下的 `lcp-ab-*.json`）：

| 指标 | 改动前 | 改动后 | 变化 |
| --- | --- | --- | --- |
| LCP 中位数 | 5152 ms（5088–5152） | 2900 ms（2860–2944） | **−43.7%** |
| 配对中位差 | — | −2252 ms | — |

前后区间完全不重叠，不是抖动。首屏图片字节数：51 kB JPEG → 21 kB WebP。

同一轮改动对另外两个页面的影响（应当为零，实测也在噪声内）：

| 页面 | 改动前 | 改动后 | 说明 |
| --- | --- | --- | --- |
| `/workspace` | 2630 ms | 2530 ms | LCP 是 `<h1>` 文字，本轮无改动 |
| `/editor/<id>` | 5690 ms | 5600 ms | LCP 是私有资源图，优化器用不了 |

这两行是单端口 3 轮采样、未交错，slow4g 档位下的往返抖动可达 ±800 ms（本轮曾出现过
同一份代码 2630 ms 与 3480 ms 两次结果）。它们只能说明「没有变慢」，不构成提升证据。

## 4. 还没做的两件事

这轮只把 `/r` 的图片路径打通了，另两个页面的瓶颈已经定位清楚，但都不是改 CSS
或加 hint 能解决的：

- **`/editor`**：LCP 同样是放置图，但它是私有资源，走不了公开优化器。可行方向是
  在资源路由上按 `w` 参数用 sharp 转码并做进程内缓存，与公开侧对齐（需要处理
  多尺寸缓存、缓存失效和 `srcset` 与预载的一致性）。这轮没有做，因为它是用户
  简历里的图片，转码质量与缓存失效需要单独评估。
- **`/workspace`**：LCP 是标题文字，首屏要同时下载 24 kB 样式与 184 kB（gzip）JS，
  在 409 kbps 下光是传输就要 ~4 s。去掉框架基线之外，剩下的都是首屏内容本身
  （简历卡片），继续拆分的收益不足以抵消交互复杂度。

## 5. 复查方式

```bash
# 1. 两个端口分别启动改动前 / 改动后的构建（都指向同一份 file 后端）
# 2. 造固定数据
node scripts/seed-perf-fixtures.mjs http://127.0.0.1:3210
# 3. 交错 A/B
node scripts/measure-lcp-ab.mjs \
  --a http://127.0.0.1:3211 --b http://127.0.0.1:3210 \
  --runs 5 --net slow4g
```

单端口多轮采样用 `scripts/measure-lcp.mjs`，结果落在 `.data/perf/results/`。
